The general pattern

Almost every feature touches the same three layers, in this order:

1. Model (lib/models/) — if you're storing new data (e.g. a "starred" flag on a message), add the field here first, plus to toMap()/fromMap() if it needs to persist.

2. Service (lib/services/) — the logic that talks to the API or the database. UI code should never call http or sqflite directly — it goes through a service.

3. Widget/Screen (lib/widgets/, lib/screens/) — the UI that calls the service and displays the result. chat_screen.dart is the one place that holds app-wide state (_messages, _conversations) and passes it down to widgets as props.

Worked example: adding a "regenerate response" button

1. Service — gemini_service.dart already exposes sendMessageStream(). No new service code needed — you're just calling the same method again.

2. Screen — in chat_screen.dart, add a method _regenerateLast() that removes the last model message from _messages and re-runs _handleSend() with the previous user message's text.

3. Widget — in message_bubble.dart, add a small icon button (only shown when !message.isUser) that calls a new callback prop, e.g. onRegenerate, passed down from chat_screen.dart.

Adding a new database field

Since the schema is created once in storage_service.dart → _initDb(), changing it after the app has already shipped needs a migration, not just an edit. The simplest approach for a hobby project:

return openDatabase(
  path,
  version: 2,  // bump this
  onCreate: (db, version) async { /* ...existing tables... */ },
  onUpgrade: (db, oldVersion, newVersion) async {
    if (oldVersion < 2) {
      await db.execute('ALTER TABLE messages ADD COLUMN starred INTEGER DEFAULT 0');
    }
  },
);
Anyone with the old app version installed will run this migration automatically the next time they open the updated app — their existing conversations won't be lost.

Adding a new dependency

Add it to pubspec.yaml under dependencies:, then run flutter pub get locally, or just push — GitHub Actions runs flutter pub get automatically as part of the build, so you don't need to do anything extra there.

Testing a change before pushing

Since you're building via GitHub Actions rather than locally, the fastest sanity check before a push is flutter analyze — but that needs a local Flutter install. Without one, your real test loop is: push → check the Actions tab → read the build log if it fails. Slower, but works fine for a project this size. If you find yourself iterating a lot, installing Flutter locally later (once you have more data budget) will save real time.
